# 数据包解析手册（公开版）

X 官方数据包（设置 → 你的账号 → 下载你的数据存档）是一个 zip，解压后核心是一个 `data/` 目录，里面几十个 `.js` 文件。它们不是普通 JSON：每个文件形如

```
window.YTD.tweets.part0 = [ {...}, {...} ]
```

解析方法：读全文 → 去掉 `window.YTD.<名>.part<数字> = ` 前缀 → 剩下的按 JSON 解析为数组。有的大文件分多个 part（part0、part1…），按序号合并。每个数组元素是一层包装对象，真正的记录在它的同名键里（如 `{"tweet": {...}}`）。

**文件匹配纪律（先读这一条，能省一次翻车）**：只按**完整文件名精确匹配**目标文件，**禁止按前缀模糊匹配**。`data/` 里有大量同前缀的无关文件——如 `account-creation-ip.js`、`account-label.js`、`account-suspension.js` 都是独立文件，不是 `account.js` 的分片；按前缀 glob 会把它们误读进来，轻则解析失败，重则数据污染。分片的真实形态：先列出 `data/` 全部文件名看清命名，只收目标文件本体与其文件名中明确带 part 序号的分片，按 part 序号从小到大合并；拿不准某个文件是不是分片时，先看它的第一行 `window.YTD.<名>.part<数字>` 赋值名，对得上才收。


**性能纪律**：数据包文件逐个处理、中间结果逐个落盘，不许把全部 `.js` 一次性载入内存；`tweets.js` 等大文件按条目分块解析。包再大也按这个节奏走，不许为了省事整包读入。
## 本审判要用的文件

| 文件 | 包装键 | 用途 |
|---|---|---|
| `account.js` | `account` | 账号自认：`username`、`accountId`、`createdAt`、显示名（`accountDisplayName`，缺失时以 `name` 字段兜底）。包内可能另含 `email` 等隐私字段——不使用、不写入任何产物。一切判决以这里的账号为准 |
| `tweets.js` | `tweet` | 审判主体：全部帖子 |
| `follower.js` | `follower` | 关系侧参考：粉丝的 accountId 列表 |
| `following.js` | `following` | 关系侧参考：关注中的 accountId 列表 |
| `like.js` | `like` | 可选：点赞过的帖子（tweetId），本审判一般不用 |

其余文件（私信、广告、个人化数据等）**不要打开、不要导入产物**——审判用不到，打开只是徒增隐私暴露面。

## tweets.js 单条记录的字段（示例为虚构）

```json
{"tweet": {
  "id_str": "1900000000000000001",
  "created_at": "Sat Oct 11 10:00:00 +0000 2025",
  "full_text": "正文……",
  "favorite_count": "12",
  "retweet_count": "0",
  "in_reply_to_status_id_str": "1900000000000000000",
  "in_reply_to_user_id_str": "1111111111",
  "in_reply_to_screen_name": "someone",
  "edit_info": {"edit": {"editControlInitial": {"editTweetIds": ["1900000000000000000", "1900000000000000001"]}}},
  "entities": {
    "urls": [{"expanded_url": "https://x.com/other/status/1900…", "url": "https://t.co/xxxx"}],
    "user_mentions": [{"screen_name": "someone", "id_str": "1111111111"}],
    "hashtags": [{"text": "话题"}]
  }
}}
```

注意：数值字段在包里是**字符串**，用前转数字。`created_at` 是 UTC 时间，展示时换算成使用者的时区；**无法得知使用者时区时，用 UTC 并在产物里注明「日期按 UTC」**，不许默默选一个时区。

## 编辑链：一条帖的多个版本（先合并，再计数）

数据包是**按版本逐条记录**的：一条被编辑过的帖，它编辑前后的每个版本在 tweets.js 里各占一个条目、各有自己的 `id_str`，版本之间只靠每条记录的 `edit_info` 字段互相指认。不先把版本合并，后面所有计数与聚类都会把一条帖数成多条。

- **建链方法**：读每条记录的 `edit_info`——最新版记录里是 `edit_info.edit.editControlInitial.editTweetIds`，初始版本记录里是 `edit_info.initial.editTweetIds`；两个位置装的都是同一份「本帖全部版本号列表」（按编辑先后排列）。把同一份列表里出现过的全部 ID 归为一条编辑链；列表长度 >1 的，就是被编辑过的帖。未编辑的帖列表里只有自己一个 ID，自成单条。**edit_info 缺省口径**：若包内记录整体没有 edit_info 字段（旧格式包或导出异常），视为无版本链数据——每条记录自成一条逻辑帖，对账时明示「编辑链不可考」；疑似改字重发只能靠判定手册的聚类灰区复核兜底，不许假装已经合并。
- **审判单位 = 逻辑帖**：一条编辑链 = 一条逻辑帖。一律以链尾（列表最后一个）ID 作为这条帖的编号，以链尾记录的文本、时间、点赞数为准做分类、筛查与判决；旧版本不是独立帖——不单独计数、不单独判决、不单独出现在任何产物里。
- **对账新增四项**（与原有对账一起报给用户）：条目总数（tweets.js 记录数）、编辑链条数（链长 >1 的链数）、旧版本条目数（各链长度减一之和）、逻辑帖总数（＝条目总数 − 旧版本条目数）。后续一切总数、分布与产物计数都以逻辑帖为准。

## 分类判定程序（按顺序，命中即停）

1. **转帖**：`full_text` 以 `RT @` 开头。
2. **回复**：`in_reply_to_status_id_str` 非空。其中 `in_reply_to_user_id_str` 等于本账号 accountId 的，为**自回复**。
3. **引用**：非回复，且 `entities.urls` 里有指向 `x.com/<他人>/status/<id>` 或 `twitter.com/…/status/…` 的链接（即引用了别人的帖子并带自己的评论）。指向自己帖子的链接不算引用，算主贴（自引）。
4. **主贴**：以上都不命中。

**自回复链重建**：自回复按 `in_reply_to_status_id_str` 逐级上溯，直到链头是一条主贴/引用（或父帖不在包内）。整条链算一个帖子单位：判决以链为单位展示，链内成员跟随链头所在分组；父帖不在包内的自回复，独立按回复处理。

## 时间与计数口径

- 帖子总数以**逻辑帖**计（见上「编辑链」一节）：条目总数 = tweets.js 记录数，逻辑帖总数 = 条目总数 − 旧版本条目数。解析后先对账：逻辑帖总数、四类计数之和（以逻辑帖计）、编辑链条数、旧版本条目数、时间范围（最早/最晚一条）都要报给用户核对，对不上不许继续。
- 每条版本记录在包里只出现一次；被编辑过的帖会有多条版本记录，属正常现象，按编辑链合并即可。**注意包是导出快照**：导出后被删的帖不在包里（正常）；编辑旧版本留在包里是版本记录，不是另一条帖（见判定手册「编辑版本边界」）。

## 常见坑

- part 文件不止一个时漏读 part1 → 总数对不上，对账环节会暴露。
- 按前缀模糊匹配文件，把 `account-*.js` 一类同前缀文件误当分片读入（见文首文件匹配纪律）。
- 把 `in_reply_to_screen_name` 当回复对象 ID 用：要用 `in_reply_to_user_id_str`。
- entities.urls 里混有普通外链：引用判定只认 x.com / twitter.com 的 /status/ 链接。
- 数字字段是字符串：直接比大小会按字典序出错，先转数字。
- 不建编辑链、拿条目数当帖子数：被编辑过的帖会被数成多条，总数虚增，同文聚类还会把同帖多版误当连发簇（见判定手册第三节警示）。
